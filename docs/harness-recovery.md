# Harness 恢复验证

## 事故链路

2026-09-26 的餐厅筛选请求先获得搜索结果，随后多次搜索失败；点评入口返回了其他城市的内容，另一来源返回空正文。Pi 在第 8 轮工具调用后直接结束，没有最后的助手正文。空字符串又被最终校验当作成功接受，Python 因无正文把任务标成失败，Telegram 仅发送通用的“请稍后重试”。

失败请求没有写入原 `history`。用户追问时，模型读到了旧图片对话和始终注入的媒体证据。实跑还发现：即使模型已提及餐厅失败原因，只要夹带旧图片声明，媒体校验也会用图片自查指令覆盖整个回答。

## 修改

- 上下文按当前用户、当前聊天的真实任务顺序恢复，包含旧版本遗漏的失败请求。最近任务摘要包含请求、状态、错误和有限的来源线索，不载入整页正文或私人文件内容；`/reset` 设置新的上下文边界。
- 搜索依次尝试 Bing、DuckDuckGo、Brave，并报告各来源的结果类别。连续两次完整搜索失败后停止重复调用搜索通道；连续两次没有新增来源时，也停止换词空转，网页读取仍可用。空页、明显的短验证页标为不可用资料。
- 常规执行限制为 12 轮、24 次工具调用；额度耗尽、空回复或模型中断后保留无工具收尾机会。模型请求限制 90 秒；一次推理中断在原上下文上恢复，不从头重放整个任务。
- 对最近一次失败的只读检索，直接追问失败原因或要求继续会恢复原目标并进入搜索，只开放检索、读取、计算与任务核查，不重放有副作用的操作。
- 在有工具失败且模型提前放弃时，最多补救两次。对于已观察到的检索任务，“是否需要我重试”会被要求继续只读检索；没有扩大文件写入、发消息、终端等权限。
- 媒体校验按任务范围处理。无关媒体声明的修复指令要求回到原请求，禁止引导模型查旧图片。
- 分差与阈值比较使用 `calculate`，以十进制（50 位精度）执行四则运算与比较，拒绝代码、变量、函数和幂运算。测试包含 `4.6 - 4.3 == 0.3` 为真、`4.3 < 4.6 - 0.3` 为假；来源真实性仍须单独核验。
- 最终答复不能为空。异常通知包含本次请求与记录中的具体原因；失败也保存在上下文里。运行轮次、工具数与限额状态写入 `run_summary`。

## 自动化与实跑

当前完整测试集 98 项通过，包含失败恢复、用户隔离、媒体交付与评分计算边界检查。

`tests/test_recovery.py` 通过实际 Pi/Node 运行时连接确定性的本地 SSE 模型，覆盖工具预算耗尽后的正文、模型出错续接且不重复工具、空输出恢复、工具失败后的补救。另覆盖搜索来源切换、连续失败停止重复查询、失败上下文、用户隔离、重置边界、异常通知与无关媒体校验。

`scripts/test_harness_recovery.py` 使用真实本机 Qwen + Pi，注入可重复的检索故障和明确标为软件测试的评分资料，验证失败追问归属与失败后继续读取、计算分差。结果写入 `runtime/harness-recovery/report.json`。该测试不发送 Telegram 消息，不代表已取得大众点评真实店铺评分。运行前停止 Bot，运行后恢复服务，避免争抢推理资源。

```sh
.venv/bin/python -m pytest -q
.venv/bin/python scripts/service.py stop
.venv/bin/python -m scripts.test_harness_recovery
.venv/bin/python scripts/service.py start
```

公开搜索通道另做过在线检查，Bing 返回了 5 条结果。完整 Telegram 交互、用户登录态和大众点评真实分项评分获取没有在本次测试中完成。当前 Bot 仍没有登录浏览器操作能力；改动保障恢复流程、上下文与诚实交付，不能保证外部网站始终可访问。重复放弃检测与媒体范围检查仍是有限的规则，不是通用语义验证器。
