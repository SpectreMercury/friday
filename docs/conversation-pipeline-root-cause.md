# 对话执行链根因与修复

这次故障涉及消息持久化、模型上下文、任务目标、证据核验和发送五层。
持久化记录没有被清空；先前仅修复消息帧上限和媒体证据例外，不能解决层与层之间的语义错误。

## 已复现的根因

1. **话题关联被当成待办继承。** 将本轮关联到旧任务后，合同从整段历史重新抽取目标，
   缺少当前输入边界及要求身份。已经完成的动作可能压过本次纠正或问答。
2. **证据只有类别，没有对应关系。** 原实现用“任务里存在任意读取／写入／已交付媒体”
   满足所有同类别要求；会误拒绝真实成果，也会让无关历史回执担保新要求。
3. **恢复了执行轨迹，却把它当成聊天。** checkpoint 内的内部核验提示使用 user role，
   被否决草稿使用 assistant role，下一轮原样继承。超长单轮甚至会直接得到空历史视图。
   无 checkpoint 的 history 回退也曾绕过答复核验结果，必须与正常投影共用同一接受规则。
4. **核验与交付未绑定版本。** `last_verdict` 可以被不同正文或更新后的用户输入复用；
   否决后的内部 feedback/checks 又被拼接成用户答复。“发出消息”因此不等于正常回答。
   新输入与单纯证据更新现在分别处理：前者接续真实要求，后者只对同一正文有界重审。
5. **进度和生命周期是全局布尔值。** 无关子任务能改变整单状态；重启清空工作预算，
   交替查询、重复失败和无进展核验可能反复消耗时间。
   工具批次中收到更正后，曾只阻止下一次调用；现在阻止整个旧批次剩余动作。
6. **说明缺口被当成完成原任务。** 真实模型验收复现：用户要求取得数据并说明访问缺口，
   合同只保留“说明缺口”，全部解释项通过后又把已知缺失前提清除，错误标记 completed。
   首次修复后，真实复验仍复现合同遗漏实际查询且缺口数组为空：核验器仅信任内部合同，
   没有独立检查原始请求的语义覆盖。纯建议与真实结果必须区分，核验必须同时对照原文，
   补全遗漏目标；缺口解除需要独立证据。
7. **typing 使用了不同的终止规则。** 发送超时且回执不确定后，发送队列已停止，
   typing 仍因 succeeded / delivered=0 不断刷新。现已与实际交付队列的终止状态对齐。

## 实现约束

- 合同区分本轮输入与历史背景，宿主为每项要求生成稳定 ID；当前输入不得漏项。
  已完成背景不自动成为新任务，未被取消或替换的未完成要求仍需处理。
- 独立核验先按当前原文列目标与实际缺失前提，再映射合同；遗漏目标阻止完成判定，
  经来源和 schema 校验后补回合同。实际复验仍观察到混合目标的类别标签可能粗糙，
  因此不能只凭标签或“解释写完了”判定完成；未解除的真实前提会强制 needs_input。
- 核验逐项引用带来源的真实证据 ID，校验账号、会话、输入范围、证明类型及完整性。
  文件产物、平台交付、App 会话可取和单纯排队分别记录；队列提交不算产物完成。
- `accepted` 表示答复可交付，`outcome` 由逐项事实推导。真实的部分结果或缺权限说明
  可交付；需要用户补充时停止自动修复。异步完成只结算明确监视的剩余要求。
- 跨 job 仅投影真实用户输入、通过核验的最终答复及成对工具证据；内部控制标注来源。
  同 job 恢复使用原 checkpoint；原始消息、失败草稿和原始证据不被删除。
- 最终交付绑定正文、输入和证据快照；新输入使旧结论失效。未处理补充在预算耗尽时
  回到自己的队列，不被已结束的旧执行吞掉。内部审查文本留在诊断记录中。
- 工具数、模型轮数、工作时长、核验及收尾状态持久化；无新输入的重启不重置预算。
  相同或交替无进展查询、重复错误和重复核验均有界。
  工作阶段上限 6 分钟，为末轮调用、收尾、合同生成与最多两次同正文重审预留时间。
- 仅裁剪模型视图并保留原文引用，显式说明不完整；系统索引不重复本轮全部正文。
  字符及估算 token 边界用于限制输入，不能把预览当成全量核验。
- 启动日志和每次实际运行记录源码构建指纹，验收同时检查版本、正文、结果状态和回执。
