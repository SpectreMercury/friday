**从功能机器人到通用助手：系统架构审查**

2026-09-26。审查范围是整个现有应用的主要执行路径，不以点评查询作为需求边界。依据为当前工作区的 Telegram 入口、任务存储、Pi 桥接、模型循环、工具、权限、媒体与语音调度、结果校验、交付以及测试代码。这里区分代码事实、架构判断和改造建议；本次未修改运行代码，未进行性能或故障注入实测，也不是完整安全审计。

此前的 [OpenClaw / Hermes 对照](./openclaw-hermes-design-review.md) 可作为机制参考，但围绕一个失败案例提出的整改不足以覆盖本系统。

**总体判断**

当前系统已经有可工作的本地推理、媒体生成、语音、授权、队列和发送组件；但通用助手层主要是把这些组件接到每条消息启动的 Agent 上，再用针对具体事故的规则补齐行为。

这种结构能完成部分预设路径，却没有统一管理“用户要达成的事情、当前执行现场、可用能力、等待事项和最终结果”。因此，错误会跨层传播：入口可能先选错任务类型，上下文可能关联错目标，恢复又基于错误分类继续，最后有文本就可能被认为完成。

这不是单一数据源或一句提示词的问题，也不能仅凭静态审查归咎于模型。更准确的工程判断是：功能组件已经存在，但支撑通用助手的会话、任务和能力管理仍不完整。

**一、输入层在理解请求前，替用户决定了任务**

代码事实：`LocalBot.message()` 将图片和 document 放进同一分支，尝试按图片解码，然后以视频任务入队；没有说明文字时提示重新发图片并描述视频。文字则走 chat，音频走转录后 chat。

影响不仅限于一个网站：用户发截图问问题、发图片要求分析、发 PDF 要总结，都无法经过同一套“理解内容与意图”的入口。模型再强也补救不了没有交给它的输入。

建议：渠道层只负责身份、消息、附件和引用关系的标准化。附件先作为资料保留；显式 `/video` 等命令可以确定操作，普通附件应结合用户要求决定分析、提取、编辑或生成。附件类型不能替代用户意图。

依据：[Telegram 消息入口](../local_ai/bot.py:148)。

**二、一条消息就是一个 job，缺少可持续的用户任务关系**

代码事实：普通文字每次创建独立 job、独立 Pi 进程。历史由最近的 jobs 问答重建，另注入最近三个任务的有限工具摘要。`resumable_research()` 只对特定句式和特定只读工具组合续接。数据库的父子关系主要用于媒体子任务。

缺少通用机制来可靠表示：这条消息是纠正当前目标、补充一个条件、回答一个等待中的问题，还是发起新任务。数据库有记录，不等于运行时能恢复完整执行现场。

建议：区分会话、用户任务和执行尝试。一次任务可以经历多个用户消息、多次执行尝试和多个子操作。保存原请求、最新约束、有效证据、未完成事项和关联关系；收到纠正时修订当前任务，而不是靠几个词回找上一轮。

这不要求把每个问答变成复杂工作流，也不要求模型先输出冗长计划。简单问答仍可直接完成。

依据：[任务与历史存储](../local_ai/store.py:65)、[任务上下文与续接](../local_ai/task_context.py:6)、[每轮 Pi 启动](../local_ai/pi_agent.py:180)。

**三、能力是一组固定分支，尚未形成可发现、可检查、可组合的体系**

代码事实：模型可见工具定义写在 Node 文件里，执行分支在 Python，允许的工具名又在执行校验中维护；工具能力和限制还写进系统提示词。搜索和网页读取没有通用业务 API 适配层。当前源码没有接入通用 skills、MCP 或工具注册与可用性发现机制。

影响：同一个能力需要多处同步；模型知道工具名称，却未必能可靠区分“支持此功能”“本机已配置”“凭据有效”“服务正在工作”“本次返回的数据够不够”。新增功能容易再增加一个特殊分支。

建议：统一能力注册与元数据，包括输入输出 schema、可用性、所需权限、外部服务、错误类别、是否产生副作用，以及结果核验方式。业务 API、搜索、浏览器、文件解析和本地生成可以是适配器；具体复杂流程由按需加载的技能承担。

API 优先应落实在适用能力的选择上，而不是给所有请求写死“先搜索、再浏览器”的顺序。也不能把“可通过终端做任何事”当作已经具备了全部能力。

依据：[工具定义](../pi/runner.mjs:24)、[工具执行](../local_ai/pi_agent.py:51)、[校验允许列表](../local_ai/execution.py:4)。

**四、任务排队、推理资源、外部等待和交付相互阻塞**

代码事实：一个 worker 依次处理待发送结果和下一个任务，并等待整个任务结束。Pi 的一次运行在 `engine.lock` 内完成，包含模型调用、工具执行和等待批准。批准等待最长 180 秒。图片、视频、聊天共享这个执行体系。

由控制流可推得：某个任务等待网页、等待用户确认或进行长时间视频生成时，其他普通任务及 worker 上的交付重试不能独立推进。命令入口仍能处理部分 `/status`、取消等操作，不能据此说整个进程都被同步阻塞。

建议：分别管理同会话的顺序、模型推理资源、外部 I/O、等待用户和结果发送。GPU 显存限制仍然需要严格调度，不能为了“并发”盲目加载多个模型；但 GPU 资源排他不应等于所有任务状态和发送工作全局排他。工具等待期间是否释放或保留模型驻留，应由资源调度器决定。

依据：[worker](../local_ai/bot.py:346)、[Pi 引擎锁范围](../local_ai/pi_agent.py:193)、[确认等待](../local_ai/approvals.py:14)、[模型生命周期](../local_ai/engine.py:91)。

**五、缺少统一的执行、恢复和完成语义**

代码事实与影响：

| 事实 | 系统层面的后果 |
|---|---|
| Store 初始化将全部 running 任务标为 failed，并提示重新提交 | 有失败记录，但没有通用的重启后检查与续接 |
| 普通工具记录在执行之后写入；媒体另有特殊去重逻辑 | 外部动作执行与记录之间中断时，未必能判定是否可以安全重做 |
| 多种异常被归并成“网络不可用、格式不支持或访问被拒绝” | 上层失去选择恢复策略所需的错误类别 |
| 计划、输出类型、恢复和完成判断分散在多个文件和提示中 | 多个地方可以对同一任务作出不一致判断 |
| `required_tools` 检查工具名是否出现 | 检查的是执行痕迹，不是用户要求的产物与正确性 |
| `delivered=1` 也用于撤销授权不发送、发送失败通知后停止重试 | 该字段不能单独当作结果送达证据，读取者必须同时解释其他字段 |

建议形成统一协议，至少区分：执行进度、目标满足程度、交付状态、终止原因。它们是不同维度；任务可以做完但未送达，也可以只完成部分但成功送达说明。

重试必须根据失败类型和已有证据决定：临时错误可退避，参数错误需修正，缺失能力需选择替代路径，副作用结果不明需先核对，等待用户必须能恢复到原任务。预算耗尽和用户取消也不能包装成正常完成。

原请求与验收条件不能被执行者随意降低，但计划和工具选择应允许修订。刚加入的不可修改 `plan_task` 需要重新设计，不能继续扩展成更多按工具名判断的规则。

依据：[重启处理](../local_ai/store.py:9)、[工具执行及异常回传](../local_ai/pi_agent.py:208)、[通用执行校验](../local_ai/execution.py:27)、[回答校验](../local_ai/evidence.py:105)、[交付逻辑](../local_ai/bot.py:298)。

**六、权限与自主性没有形成细粒度能力边界**

代码事实：管理员终端只有六个精确命令自动执行，其余一律逐次确认；文件写入也逐次确认。确认正确绑定用户、会话和当前任务，但批准状态在内存里。已授权工具任务如何继续与能力权限没有通用关联。

影响：即便用户已经授权一个文件整理或检索任务，正常步骤也可能不断打断用户；与此同时，批准一个 shell 命令的实际能力又很宽。

建议在保持身份隔离和副作用控制的基础上，提供范围明确的能力授权，例如本任务内允许读取指定目录、修改指定工作区，外发内容和其他高影响操作单独控制。不能仅按模型说“安全”自动放行，也不能靠把所有工具都改为免确认来获得自主性。

这是权限产品设计的缺口，并非本次已经发生越权的结论。

依据：[电脑工具边界](../local_ai/computer_tools.py:42)、[批准机制](../local_ai/approvals.py:9)。

**七、验证体系侧重组件可运行，没有足够证明助手可用**

现有测试有实际价值：覆盖授权、隔离、取消、媒体去重、回执及模拟故障，也有本地真实模型的集成脚本。但它们不能替代通用任务成功率评测。部分真实模型测试使用固定网页数据；真实网站回放脚本的断言主要检查计划和联网工具是否调用、是否避免原错误文本，并没有验收用户目标。

目前不能从“101 项测试通过”推导出能理解复杂任务，也不能从一个失败推导出模型本身不行。需要把入口、模型、工具、调度和验收分别测清楚。

评测应覆盖多任务类型与多种表达，并保留未参与规则设计的样本：

| 维度 | 跨场景样本 | 主要指标 |
|---|---|---|
| 理解 | 截图问答、文档总结、数据查询、文件操作、媒体生成、组合请求 | 正确目标与约束保留率，错误路由率 |
| 对话连续性 | 追问、修改要求、取消、切换话题、恢复旧任务 | 任务关联准确率，纠正生效情况 |
| 自主执行 | 多工具依赖、缺字段、替代来源、部分完成 | 目标完成率，不必要用户介入次数 |
| 恢复 | 网络错误、模型空响应、服务重启、结果已产生后断线 | 可恢复任务续接率，重复副作用次数 |
| 真实性 | 结果缺失、工具失败、实际未发送 | 虚假完成率，证据与结论一致性 |
| 体验与资源 | 长任务与短任务混合、等待批准、发送重试 | 排队时间、有效进展等待、任务耗时和资源占用 |

同模型、同工具条件先比较运行时；再单独比较模型和推理参数。真实端到端样本、可控故障注入和语义验收应互补，不能只保留有利的成功示例。

依据：[恢复测试脚本](../scripts/test_harness_recovery.py)、[真实回放脚本](../scripts/replay_harness_live.py)、[组件测试](../tests/test_bot.py)。

**系统改造的边界与顺序**

应保留并通过接口接入已有的本地模型服务、媒体工作流、语音组件、身份隔离及真实回执；重新审视会话、任务生命周期、能力注册、恢复和验收这些通用职责。不建议凭这份审查立刻整仓推倒重写。

第一步建立当前行为基线和跨场景验收，再决定执行核心采用成熟运行时还是继续自建。OpenClaw / Hermes 已有大量相应机制，优先验证复用其中一套的成本是合理选择；但本地模型工具协议、现有渠道、GPU 生命周期、权限与本地数据兼容性必须实测，不能先宣布迁移必然成功。两套运行时也不应简单叠加，让多个调度器争夺同一个任务。

迁移或改造宜沿一条完整路径进行：标准化消息进入 → 持续会话与任务 → 工具能力调用 → 结果核验 → 独立交付。先在隔离数据与无真实副作用的环境中比较，再小范围切换；保留旧路径和数据回滚条件。上线门槛是多个任务类别的可用性改善与关键不变量通过，不是修复截图案例，也不是代码行数或测试数量增加。

**本次审查尚未证明的事情**

上述控制流与存储事实来自代码；实际阻塞耗时、广泛任务成功率、模型贡献和替换运行时的收益仍待评测。可以确认需要系统级改造，但还不能据此宣布任何一套替代方案已验证或当前系统已修好。
