# 长对话 ValueError 修复（2026-09-27）

02:20 的失败发生在 Python 读取 Pi 子进程的单行 JSON 时。原 stdout
`StreamReader` 限制为 262144 字节，但每个 `message_end` 都发送完整对话检查点，
存储层却允许 4000000 字节。用失败任务最后保存的检查点加上最后一条真实工具回执，
可重建 275734 字节的下一帧；旧读取器会抛出
`ValueError: Separator is found, but chunk is longer than limit`。

同时，`task_evidence` 将自身历次返回值嵌入下一次导出的证据，造成查询结果递归膨胀。
模型上下文压缩又直接截断工具结果的 JSON，可能丢失末尾分页游标，诱发重复查询。

修复：

- 检查点共用 4 MB 上限，通信上限额外保留 64 KiB 封装空间；真正超限时明确报错，保留旧检查点。
- 分页导出的源不包含证据查询自身；原始查询回执仍完整保存在数据库。
- 模型视图保留证据单页和分页信息，按完整工具调用/结果组压缩历史。
- 执行异常记录代码文件、行号和函数名，不记录异常正文或局部变量；当前执行错误优先于已处理的工具错误。

回归覆盖真实 Node 子进程的 300 KB 中文消息、精确 4 MB 检查点、超界保护，
重复分页不增长、分页可达结尾、上下文压缩与调用/结果配对，以及异常诊断和错误归因。
原失败帧也已离线重放，确认旧读取器失败而新读取器逐字节读取成功。
测试与重放不向 Telegram 发送消息，也不重放历史写操作。

验收：完整 `pytest -q` 共 230 项通过（7 项既有依赖警告）；Pi 运行时预检通过。
数据库已在重启前备份。02:35:32 日志确认 `Telegram Bot ready`，随后
`Application started`；LaunchAgent 状态为 running。此次未自动重试失败的历史请求，
尚未以新的 Telegram 用户消息验证实际模型答复。

02:37 的新请求在修复后的进程中持续调用当前执行的 `task_status({})`，
把自己的 running 状态误当成需要等待的外部条件，最终于 02:52 超时。
这与上面的单行消息长度异常不同。

- 当前执行状态明确标记不可等待，并提示直接处理用户最新输入；自查记录不再改变状态摘要。
- 连续三次相同成功状态查询触发停止查询并生成回复；恢复检查点时重建检测状态。
- 收尾阶段禁用工具，只收尾一次，结果核验不能再开启同一轮查询循环。
- 历史已完成任务、同一逻辑任务的媒体交付纳入核验；内部状态查询不再挤掉实际执行证据。
