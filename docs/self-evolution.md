# Friday 的能力迭代与核心升级

## 已实现的入口

在开启 Mac 管理权限的会话中，原生 App 的「会话设置 → 能力与升级」可以发起能力需求、查看草案完整文件、确认发布、选择 MCP 和恢复历史版本。Telegram 和 App 共享同一组 evolution 工具及版本记录。用户可以直接说「为我创建一个整理会议纪要的 skill」或「创建一个将工作空间 CSV 转成统计摘要的本机 MCP」。模型生成草案后，请求确认确切版本；发布不自动改变其他会话的技能或 MCP 选择。

默认会话没有 MCP。创建、发布、读取草案和执行 MCP 都要求所有者身份以及当前 session 的 Mac 管理权限。朋友账号不能使用这些接口。App 的普通鉴权、通行密钥、CSRF 和设备撤销检查仍有效；MCP 握手后还会重新检查发布者的设备授权。

## 默认选择顺序

优先复用现有能力；已有工具能做、缺少方法或流程时用 skill。缺少真实接口或执行能力，且现有 connector / MCP 无法满足时，才创建 MCP。skill 可以组织多个已有 MCP，不需要重复包装。缺少账号授权或配置时补齐授权，不通过 MCP 绕过。只有扩展层不能解决的运行时缺陷才提出核心升级。

这一顺序写入运行时的模型指令及独立 self-evolution 技能；实现方式的判断仍由模型根据任务作出，发布批准、会话隔离和代码执行权限由宿主强制检查。

## 三种更新

| 类型 | 保存位置 | 验证与生效 |
|---|---|---|
| Skill | `~/.friday/skills/<name>/SKILL.md` | 静态格式/大小检查，确认后原子替换；旧版保留为可恢复记录 |
| 本机 MCP | `~/.friday/extensions/versions/<version>/server.py` | 先静态解析，确认后启动进程进行真实 initialize / tools/list 验证，通过才发布 |
| 核心代码 | 独立候选目录，验证后替换允许的项目文件 | 确认后由独立升级器运行完整 pytest、Pi 测试和 runner 检查，等待空闲，再切换并检查构建身份与健康 |

首版本机 MCP 使用 [官方 Python SDK 的 stdio 传输](https://py.sdk.modelcontextprotocol.io/v1/)，依赖锁定在 1.x（本次安装 1.30.0）。支持创建 Python MCP server、发现工具、按 schema 校验参数和实际调用。当前不包含远程 HTTP MCP、OAuth MCP 安装器、任意依赖下载或跨机器分发。

MCP 进程不继承 Telegram、连接器和 APNs 密钥环境变量；它获得本任务的工作目录。**这不是操作系统沙箱**：本机 Python 是用户确认后运行的受信任代码，可能访问宿主可访问的资源，因此只在管理会话开放，不提供给朋友，也不能把它描述成 connector 的细粒度资源沙箱。握手通过不代表工具业务逻辑正确；代码启动本身可能产生副作用，失败后不会自动重试或假装回滚外部操作。

任务入队时捕获已启用 MCP 的发布版本；更新后新任务使用新版，原任务与续接使用原版本。每次调用再次检查当前会话绑定，撤销后阻止后续调用。技能沿用已有任务快照机制。派生会话不复制 MCP 授权。新增 self-evolution 技能只安装进库，用户自行选择启用。

## 核心升级不由被升级的进程执行

独立 LaunchAgent：`local.friday.updater`。可执行源码安装在 `~/.friday/updater/worker.py`，只依赖 Python 标准库，不导入运行中的 Friday。核心候选不能改这个升级器、数据库层、认证/授权层、启动项、密钥、依赖锁或安装包。允许的文件由升级器与服务端的固定清单共同约束，包括代理、模型引擎、媒体、语音及部分工具实现。

流程：

1. 固定草案内容、基础版本和 SHA-256 编号；确认绑定具体编号。后续源码变化会使发布失效。
2. 复制代码及现有测试到独立目录，不复制生产 `.env`、数据库、用户文件或模型权重。测试进程不继承服务凭据，不执行模型指定的任意 shell 验证命令。
3. 运行完整后端 pytest、Pi 单元测试和 runner 检查。失败只记录失败，继续使用旧服务。保留受保护的本机 `validation.log`。
4. 停止接入新的执行与实时语音，等已有运行任务及语音结束；新文字任务仍可入队。最长等待 30 分钟，超时取消本次升级。
5. 保存代码恢复清单和 SQLite 一致性快照，再停旧服务、原子替换各文件并启动。
6. 新进程须连续通过 15 次健康检查（约 30 秒），同时构建标识必须匹配候选；失败恢复旧代码并检查旧服务。
7. 升级器在文件切换期间退出，重新启动时读取持久状态并恢复旧代码。切换前退出则将草案标记失败，不偷偷重新运行测试。

暂停接入使用到期租约，升级器消失不会永久禁止处理新任务。自动回退不会覆盖生产数据库，避免丢失升级期间的请求。备份用于人工灾难恢复，不是自动还原全部用户数据。多文件替换不具备单次文件系统事务，但服务在替换期间停止，持久恢复清单覆盖半途退出。

核心升级可在 App 中「撤销此次升级」：基于升级前文件生成新的审阅草案，再经测试和确认发布。如果文件之后又被修改，拒绝直接覆盖，要求合并处理。

## 状态与通知

- staged：只有静态检查，未执行代码。
- queued / testing / waiting_idle / applying：尚未完成。
- published：技能或 MCP 已发布；是否可用仍取决于当前会话启用清单。
- succeeded：核心代码验证与启动健康检查通过。
- failed：本次未发布；查看报告。
- rolled_back：已恢复旧代码并通过旧服务健康检查。
- rollback_failed：自动恢复未成功，需在 Mac 上处理。

核心升级成功、失败或回退通过原会话事件同步，APNs 已配置时也使用原会话通知卡片；测试进度不连续推送。不通过通知直接批准新代码。

## 运维与验收范围

安装独立升级器：`.venv/bin/python scripts/install_updater.py`。安装器不会覆盖不同内容的已安装升级器，避免核心升级顺便修改恢复机制；升级器自身需在无待处理升级时人工维护。日志为 `~/.friday/updater/supervisor.log`，候选、测试日志、恢复清单与数据库快照位于 `runtime/upgrades/<revision>/`。

已验证：真实 MCP 子进程握手/调用、工具参数检查、任务版本固定、会话隔离、凭据不继承、撤销；真实 HTTP 发布接口；测试失败保留旧版、模拟健康失败回退、半途切换恢复；独立目录中的完整候选测试流程。故障测试中的 launchctl 和健康结果使用可控替身，没有故意破坏生产服务。生产服务及独立升级器已分别启动并核对构建/心跳。

测试与启动健康检查不能证明模型回答质量、所有外部工具行为或任意代码绝对安全。当前没有自动依赖升级、数据库迁移、升级器自修改或 iPhone 安装包热更新。原生 App 代码变化仍需要重新签名安装。
